# Character Check — план реализации

## Контекст

Нужен инструмент, который отвечает на один вопрос: **«есть ли среди этих пилотов цино-алт?»**

Исходная идея была помечать таких пилотов через ESI в корпоративные контакты со стендом −10 и тагом. Это оказалось невозможно, и вокруг этого пришлось перестроить весь замысел. Итоговая проверенная картина:

| Проверено живьём (2026-08-18/19) | Следствие |
|---|---|
| `POST /corporations/{id}/contacts` → **405**, `Allow: GET`. Скоупа `esi-corporations.write_contacts.v1` **не существует**. ESI issue #751 «Manage corporation and alliance contacts» открыт с 2018, помечен «Approved by GD», воз и ныне там | Корп-контакты через ESI писать нельзя вообще. Личные контакты (`esi-characters.write_contacts.v1`) писать можно, но лимит ~1024 и лейблы не применяются, если чар оффлайн (issue #171, открыт с 2016) |
| Чатлог локала содержит **только реплики** — ни ростера, ни join/leave. `Channel ID: local`, имя канала локализовано («Локальный») | Watchdog на логах не увидит молчаливого цино. Ростер локала достаётся только копированием списка участников или OCR |
| RedisQ отключён 31.05.2026 | Стрим килмейлов пришлось бы строить на R2Z2/killmail.stream — но в новой концепции он не нужен вовсе |
| `/asearch/` умеет фильтр по items и возвращает 151 байт вместо 529 КБ… но за Cloudflare challenge (403 из любого не-браузера), CORS прибит к своему домену, в вики не документирован. И главное — `cron/6.itemcleanup.php`: `$keepPerItem = 100000`, индекс предметов хранит только последние 100k килов на тип (≈18 мес). На реальном пилоте asearch вернул 14 цино-лоссов против 16 при полном скане | Использовать нельзя: молчаливые ложноотрицательные ответы на вопрос «когда-либо» |

Отсюда финальная концепция: **локальное приложение в трее, без сервера и без базы всех килмейлов**. Пользователь копирует ники из локала (или один ник) — приложение по требованию анализирует килборд каждого и показывает, кто светил цино.

## Что считаем уликой

По каждому пилоту три независимых признака, все извлекаются из одних и тех же скачанных килмейлов:

| Код | Признак | Откуда |
|---|---|---|
| **A** `cyno_fitted` | Умирал на корабле с цино-модулем в хай-слоте | `victim.items[]`: `item_type_id ∈ {21096, 28646, 52694}` **и** `27 ≤ flag ≤ 34` **и** `depth == 0` |
| **B** `hull_lost` | Умирал на хулле, способном нести цино | `victim.ship_type_id ∈ hull_types ∪ group(hull_groups)` |
| **C** `hull_flown` | Участвовал в убийстве на таком хулле | `attackers[]` где `character_id == наш` → его `ship_type_id` |

Итоговый уровень: **RED** при A, **ORANGE** при B или C, **GREY** если ничего. В окне показываем не просто вердикт, а **список кораблей с датами** — как и просили.

Три ловушки, найденные при проверке SDE и реальных килмейлов, каждая обязана стать тестом:

1. **`depth == 0` обязателен.** Вложенные предметы наследуют флаги хай-слотов: собранный корабль в Ship Maintenance Bay даёт `flag 28` на глубине 1. Без этого фрейтер, везущий зафиченный рекон, читается как «цино зафичен».
2. **Флаг не уникален на слот.** Заряженные боеприпасы несут флаг своего модуля — на одном флаге 27 может быть и модуль, и 52 единицы ракет. Членство решается парой (type_id ∈ set) И (диапазон флагов), никогда флагом отдельно.
3. **Группы и типы держим раздельно.** Venture (32880) — группа **25 «Frigate»**; Etana (32790) и Rabisu (42245) — группа **832 «Logistics»**. Одна неаккуратная развёртка типа в его группу превращает в «цино-способные» все T1-фрегаты и все логисты игры.

### Цино-способные хуллы (проверено через `/universe/types/{id}/`, `dogma_attributes`)

| Модуль | Группы | Отдельные типы |
|---|---|---|
| 21096 Cynosural Field Generator I | 833 Force Recon, 894 HIC, 898 Black Ops | — |
| 28646 Covert Cynosural Field Generator I | 830 Covert Ops, 833, 834 Stealth Bomber, 898, **963 Strategic Cruiser**, **1202 Blockade Runner** | 32790 Etana, 33697 Prospect, 42245 Rabisu |
| 52694 Industrial Cynosural Field Generator | 28 Hauler, 380 DST, 1202 Blockade Runner | 32880 Venture, 89648 Venture Consortium Issue |

Списки **выводим из SDE, а не хардкодим**: атрибуты `canFit*` резолвим **по имени** (`dgmAttributeTypes.attributeName LIKE 'canFitShipGroup%' OR 'canFitShipType%'`), потому что помимо ходовых 1298–1300 у 28646 есть ещё 1301, **1872** (Strategic Cruiser) и **1879** (Blockade Runner). Хардкод диапазона молча теряет T3-крейсера.

Исключаем с записью причины в JSON: `35912` Standup (структурный модуль), `2852` Sansha Cynosural Field (NPC).

Индустриальный цино зажигает мост только для JF/Rorqual — помечаем находки по 52694 отдельным оттенком, это менее острая угроза.

## Предохранитель (guard) — отдельно, потому что от него зависит удобство

Задача: отличить «ники из игры» от любого другого текста в буфере. Четыре ступени, каждая следующая дороже предыдущей.

**Ступень 0 — нормализация.** Разбить по `\r?\n`, обрезать пробелы, выкинуть пустые строки, снять возможный `\ufeff`, дедуплицировать.

**Ступень 1 — быстрые отсечки** (любое совпадение → выход, ноль сетевых запросов):
- в тексте есть `http://`, `https://`, `www.`
- есть символы, невозможные в имени EVE: `<>{}[]|\/@#$%^&*()_+=~;:"?!,` и т. п.
- хоть одна строка содержит `\t` — это D-Scan, инвентарь или фит, не список ников
- строк больше 250 или суммарно больше 10 000 символов
- есть строка длиннее 37 символов (максимум имени персонажа в EVE)
- есть строки на кириллице — имена персонажей в EVE только латиница

**Ступень 2 — маска имени.** Регекс `^[A-Za-z0-9][A-Za-z0-9'\- ]{1,35}[A-Za-z0-9]$`, не более 2 пробелов (имя — от одного до трёх слов), нет подряд идущих `'`/`-`/пробелов. Проходной порог — **≥ 90 % строк**. *Точные правила именования CCP стоит перепроверить на реальном дампе имён при реализации; регекс намеренно чуть строже, а финальным арбитром всё равно выступает ESI.*

**Ступень 3 — сильный положительный признак.** Если среди строк есть **имя одного из твоих персонажей** — это гарантированно вставка списка локала. Имена своих чаров берём бесплатно из заголовков `Listener:` свежих чатлогов (`Documents\EVE\logs\Chatlogs`, фильтр по `st_mtime` за последние сутки) — ни строчки конфига от пользователя. Приём взят у EVE L-SCAN. Свои чары затем исключаются из анализа.

**Ступень 4 — ESI как финальный арбитр.** Только то, что прошло ступени 1–2, уходит в `POST /universe/ids/`. Имена персонажей в EVE уникальны и существуют; случайный текст их не даст. Если в ответе `characters[]` пусто — тихо выходим, ничего не показываем.

Две проверенные тонкости этого вызова:
- **Дубликаты → жёсткий 400** (`'names' items are not all unique`). Дедуп до отправки обязателен.
- **Есть нечёткое совпадение**: запрос `["Jita"]` вернул альянс *«Jita Holding Inc.»* и корпорацию *«jion ss Corp»*. Читаем **только массив `characters`** и сверяем возвращённое `name` с введённым (без учёта регистра, точное совпадение).
- Максимум 500 имён (501 → 400), но на 500 периодически ловится 504. Чанк — **150**.

**Режим одного ника** проходит те же ступени. Ложное срабатывание на случайном слове отсекается ступенью 4: ESI просто не найдёт персонажа, и приложение промолчит.

## Источники данных и бюджет запросов

| Что | Endpoint | Замерено |
|---|---|---|
| Имена → id | `POST https://esi.evetech.net/latest/universe/ids/` | 150 имён ≈ 0.5 с |
| **Первичная подсветка** | `POST https://api.eve-kill.com/characters/analyze` | **250 id за 0.53 с, 24 КБ**, отдаёт `cyno_probability` |
| Авторитетный скан | `GET https://zkillboard.com/api/characterID/{id}/losses/` и `/kills/` | ~0.8 с, ~48 КБ gzip на страницу (200 килов) |
| Резолв id → имена кораблей/систем | `POST /universe/names/` + локальный SDE | — |

`characters/analyze` от EVE-KILL даёт **первую краску за 0.6 с на весь локал**, но окно у него 90 дней: на 129 проверенных пилотов он показал `cyno_probability = 0` для шести, у которых полный скан нашёл цино-смерти (одна — 8 штук, последняя в 2017). Поэтому он **только для мгновенной предварительной подсветки**, никогда не финальный ответ.

Жёсткие ограничения, проверенные живьём:
- **Пустой `User-Agent` на zkb → 403.** UA с контактом обязателен, иначе процесс не стартует.
- `Accept-Encoding: gzip` — сжатие в 8.4 раза (55 КБ против 465 КБ). Обязательно.
- Конкурентность к `zkillboard.com/api` — **8** (проверено 231 запросом подряд без единого 429; на 8 воркерах вышло ~8–10 req/s). Хардкод-константа, не настройка.
- Пагинация: 200 килов на страницу, **потолок 100 страниц**. `pastSeconds` ограничен 7 сутками. Запятые в id больше не поддерживаются.
- `no-items` и `no-attackers` **отключены навсегда** — лёгкого варианта ответа нет.
- `r2z2.zkillboard.com` — **отдельный бакет, 15 req/s, бан до часа**. В этой концепции он не нужен: не трогаем вообще.
- 41 % активных пилотов упираются в 200 строк на первой странице `/losses/` и требуют вторую. Бюджет — ~1.4 запроса на пилота.

### Адаптивная глубина

- **Один ник** — качаем всю историю (до потолка в 100 страниц), останавливаемся раньше при подтверждённом A.
- **Список из локала** — первая страница `/losses/` + `/kills/` на каждого, результаты стримятся в окно по мере поступления (первые ответы через 5–10 с). Дозагрузка остальных страниц идёт фоном, строки в таблице обновляются на ходу. Пилот с уже найденным A не дозагружается — вердикт не может стать хуже.

### Кэш

Ключевое свойство: **все три признака монотонны — став истиной, они ею и остаются.** Пилот, однажды умерший с цино, не может «разумереть».

- Позитивы кэшируются **навсегда**, по `character_id`. Помеченного пилота не перезапрашиваем никогда.
- Негативы — с TTL (7 дней) и запомненным `newest_killmail_id`. На повторной вставке одного `POST /characters/analyze` на весь состав (0.6 с, 1 запрос) хватает, чтобы увидеть, что счётчики килов не изменились, и пропустить поход в zkb.
- Итог: повторная вставка того же флота — **один запрос и меньше секунды**. Флот на 250 пилотов при 80 % попаданий в кэш падает с ~50 с до ~10 с.

## Схема кэша (SQLite, `%APPDATA%\CharacterCheck\cache.db`)

```sql
CREATE TABLE pilots (
  character_id     INTEGER PRIMARY KEY,
  name             TEXT NOT NULL,
  name_lc          TEXT NOT NULL,          -- casefold(), ключ поиска
  level            TEXT NOT NULL,          -- red | orange | grey
  has_a INTEGER, has_b INTEGER, has_c INTEGER,
  pages_scanned    INTEGER NOT NULL DEFAULT 0,
  full_history     INTEGER NOT NULL DEFAULT 0,  -- дошли до конца пагинации
  newest_killmail_id INTEGER,
  checked_at       REAL NOT NULL,
  corp_name TEXT, alliance_name TEXT
);
CREATE INDEX idx_pilots_name_lc ON pilots(name_lc);

CREATE TABLE findings (                    -- то, что показываем в окне
  character_id INTEGER NOT NULL,
  killmail_id  INTEGER NOT NULL,
  kind         TEXT NOT NULL,              -- fitted | cargo | hull_lost | hull_flown
  ship_type_id INTEGER, module_type_id INTEGER,
  km_time      REAL NOT NULL, system_id INTEGER,
  PRIMARY KEY (character_id, killmail_id, kind)
) WITHOUT ROWID;
CREATE INDEX idx_findings_char ON findings(character_id, km_time DESC);

CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT);
```

`name_lc` намеренно **не UNIQUE**: имена биомассированных персонажей могут освобождаться и переиспользоваться, а UNIQUE превращает это редкое событие в падающий INSERT. Причину записать комментарием прямо в схеме.

## Интерфейс

Трей на PySide6. Клик по иконке — окно результатов; оно же всплывает само, когда скан нашёл RED.

Таблица: **ник | вердикт | корпа/альянс | корабли с датами**. Строка раскрывается в список находок (`Falcon — Covert Cyno — 2026-02-16`), двойной клик открывает килмейл на zkb в браузере. Пока идёт дозагрузка — строка помечена «уточняется». Звук при первом RED в скане (`winsound.PlaySound`, отдельный сигнал на уровень) — это единственное, что замечаешь, глядя в игру.

Настройки: UA-контакт, TTL негативов, глубина для списка, звук вкл/выкл, автозапуск.

## Фазы

**Фаза 0 — полдня, без GUI.** Сгенерировать и глазами проверить `cyno_sets.json`. Снять фикстуры: реальный килмейл с цино в хай-слоте, килмейл с вложенным предметом на `depth 1` с флагом 28, Venture с индустриальным цино, чатлог `Локальный_*.txt` (копировать через `shutil`, не через редактор), реальная вставка списка локала из игры, D-Scan, EFT-фит, кусок кода, русский текст. Проверить регекс имени на реальном списке ников.

**Фаза 1 — рабочий срез.** `guard.py` + `clipboard.py` + `esi.py` + `zkb.py` + `analyze.py` + `cache.py` + `console.py`. Ни строчки Qt. Копируешь локал — в консоли появляется список цино-пилотов. Это уже весь продукт по сути; всё дальнейшее — удобство.

**Фаза 2 — трей и окно.** `ui/tray.py`, `ui/results_window.py`, звук, автозапуск, настройки.

**Фаза 3 — скорость.** EVE-KILL `characters/analyze` для мгновенной первой краски, фоновая дозагрузка страниц со стримингом в таблицу, прогресс-бар.

**Фаза 4 — по желанию.** Экспорт списка, история сканов, ручной ввод ника в окне, горячая клавиша.

**Осознанно не делаем:** запись контактов через ESI (невозможно для корпы, бесполезно для личных), OCR локала (отдельная большая тема, вернуться после Фазы 3), любой стрим килмейлов и своя база всех килов, сервер.

## Тесты

`python -m unittest discover -s tests`, всё без сети.

- **`test_guard.py` — главный.** По фикстуре на каждый вход: список локала → принят; один ник → принят; свой ник в списке → сильный признак сработал; D-Scan → отбит по табу; EFT-фит → отбит; URL → отбит; кусок кода → отбит; русский текст → отбит; 300 строк → отбит; строка в 40 символов → отбита.
- **`test_analyze.py`** — матрица A/B/C и три ловушки поимённо: `depth 1, flag 28` → **не** A; заряд на флаге 27 → не считается вторым цино; Venture + индустриальный цино → A; голый Rifter (группа 25) → GREY; жертва без `character_id` → пропуск.
- **`test_cyno_sets.py`** — сборка из `fixtures/sde_mini.db`; проверить, что 1301/1872/1879 подхвачены, что 35912 и 2852 исключены **с записанной причиной**, что ни один `canFitShipType` не утёк в `hull_groups`.
- **`test_zkb.py`** — пагинация, остановка на пустой странице, потолок 100, отсутствие UA → ошибка на старте.
- **`test_cache.py`** — миграции прогоняются дважды без ошибок; позитив не перезапрашивается; TTL негатива истекает.
- **`test_chatlog.py`** — UTF-16LE с BOM, `\ufeff` в начале **каждой** строки, повторяющийся блок заголовка, извлечение `Listener:`, отказ на корп-логе.
- **`test_headless.py`**, **`test_no_input_automation.py`** — два инварианта, исполняемые.

Не покрывается автотестами и уезжает в `docs/MANUAL_TESTS.md`: реальный round-trip копирования из игры, поведение звука в полноэкранном режиме, точность вердикта на пилотах с заведомо известной историей.

## Проверка результата

1. `python sde/build_cyno_sets.py` → глазами сверить `cyno_sets.json` с таблицей хуллов выше.
2. `python -m unittest discover -s tests` → зелено.
3. `python -m core.console` → скопировать в игре список локала (клик по нику в списке участников, Ctrl+A, Ctrl+C) → в консоли список с вердиктами.
4. Контроль по известному пилоту: взять `character_id` с подтверждёнными цино-смертями, сверить вывод приложения с `https://zkillboard.com/api/characterID/{id}/losses/` вручную.
5. Проверить предохранитель: скопировать URL, кусок кода, русский текст, D-Scan — приложение обязано промолчать, **не сделав ни одного сетевого запроса** (проверяется по логу).
6. `python main.py` → иконка в трее, вставка локала поднимает окно со списком и звуком.

## Риски

1. **Ложноотрицательные молчаливы и вечны.** Цино-алт, ни разу не потерявший корабль и ни разу не попавший в килмейл, невидим. Честная формулировка в README — «известные цино-алты».
2. **Признак C шумит.** «Летал на Force Recon» — это половина активных PvP-пилотов. Поэтому C даёт только ORANGE и по умолчанию таблица сортируется RED → ORANGE → GREY, а не по алфавиту.
3. **Скан 200 пилотов — это ~400 запросов.** Держим конкурентность 8, gzip и кэш; при первых 429 снижаем и логируем громко.
4. **zKillboard может изменить правила.** Единственный источник истины по истории — один сервис. Смягчение: клиент zkb изолирован в `core/zkb.py` за узким интерфейсом, EVE-KILL уже подключён вторым источником для быстрой подсветки.
5. **Правила именования EVE в регексе — единственное непроверенное место в предохранителе.** Смягчение: ESI как финальный арбитр, регекс намеренно строже необходимого.
